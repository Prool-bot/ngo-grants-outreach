# NGO Grants Outreach CRM

Початковий модуль v0.3: моніторинг закупівель Громадського Простору, ГУРТ, Prozorro та TED, дедуплікація посилань, запис у CRM та перевірка підключення до Gmail. **Зовнішнє надсилання пошти вимкнено.** Оголошення реєструються для оцінки; тендерні контакти не використовуються для сторонніх пропозицій. 

## Розгортання
- GitHub Actions: тести під час push; workflow_dispatch для режимів check, monitor, preview, smtp-check, smtp-self-test, sources-check, imap-check.
- У Settings → Secrets and variables → Actions → Secrets задати GOOGLE_SERVICE_ACCOUNT_JSON, CRM_ID, EXPECTED_GMAIL, EMAIL_ADDRESS, EMAIL_APP_PASSWORD. Не публікувати їх або контакти в репозиторії.
- Для CRM і PDF використовується службовий акаунт Google: увімкнути Sheets API і Drive API, надати доступ редактора до CRM та читача до PDF. JSON ключ зберігається лише у GitHub Secrets. Не надавати службовому акаунту доступ до пошти. Підключення ChatGPT не передається до GitHub.
- Спочатку вручну запустити workflow з mode=check; після успіху — mode=monitor в робочий час.
- Підключити cron-job.org тільки після живого тесту: POST https://api.github.com/repos/Prool-bot/ngo-grants-outreach/actions/workflows/outreach.yml/dispatches
- Timezone Europe/Istanbul, 0 9-17 * * 1-5. JSON body: {"ref":"main","inputs":{"mode":"monitor"}}.
- Headers: Authorization: Bearer <fine-grained PAT with Actions: write for this repository>, Accept: application/vnd.github+json, Content-Type: application/json. Токен зберігати тільки в захищених налаштуваннях планувальника.
- HTTP успіх — лише прийняття запуску. Перевірити результат Actions і запис у вкладці «Системний журнал».

## Перевірка наявної SMTP-авторизації
У старому ngo-grants-bot використовуються EMAIL_ADDRESS та EMAIL_APP_PASSWORD. Ці ж назви секретів підтримує новий модуль. Секрети старого репозиторію не доступні новому автоматично. Задайте EMAIL_ADDRESS, EMAIL_APP_PASSWORD та EXPECTED_GMAIL у новому репозиторії через Settings → Secrets and variables → Actions. Не розкривайте пароль у чаті, логах або коді.
Режим smtp-check перевіряє відповідність акаунта та авторизацію SMTP без надсилання. Режим smtp-self-test надсилає один технічний лист лише на власну адресу. Для CRM і Drive застосовано окремий службовий акаунт. Для читання пошти режим imap-check перевіряє лише можливість підключення до INBOX без читання повідомлень. Попередній тест IMAP завершився TimeoutError; IMAP не є обов’язковим для моніторингу закупівель.

## Межі версії
Моніторинг працює тільки Пн–Пт з 09:00 до 17:59 Europe/Istanbul. Не збирає адреси та не здійснює зовнішніх розсилок; можливий окремий тестовий лист лише власнику. Аналіз архівів, ідентифікація організацій, окрема черга погоджених контактів, обробка відповідей та повернень ще не реалізовані. Перед будь-яким зверненням потрібна належна підтверджена підстава, перевірка відмов і виключень.

## Джерела без витрат на пошукові API (v0.2)
- Громадський Простір та ГУРТ: читання дозволених публічних сторінок.
- Prozorro: офіційна публічна стрічка закупівель, обмежена вибірка останніх змін і профільні CPV.
- TED: офіційний Search API, без ключа; вибірка за CPV за останні 7 днів.
- Режим sources-check тестує доступність двох API, без запису в CRM, без надсилання. Логи містять лише кількість та статус.
- Публічний запис закупівлі не є згодою на рекламу. Код не збирає адреси. Не використовує Tavily, Exa, Gemini чи інші спільні квоти. Джерела обмежені і не є повним вебпошуком.
- Пошукові ліміти, помилки API та порожні вибірки відображаються окремо; 0 релевантних закупівель може бути нормальним результатом.

## Інтеграційний тест v0.3
При push у main запускається check: перевірка CRM, завантаження оригінального PDF, тестовий рядок системного журналу та його повторне зчитування. IMAP перевіряється окремим ручним запуском. SMTP, API та журнал тестуються без зовнішнього надсилання. Не вмикати зовнішній cron до успішного тесту CRM.

## v0.4: тест повного циклу пошуку без запису
Режим `preview` читає реєстр закупівель, перевіряє чотири джерела, рахує знайдені та нові оголошення після дедуплікації. Не пише в CRM, не надсилає пошту і доступний поза робочим часом. Нуль знайдених позицій не прирівнюється автоматично до помилки. У режимі `monitor` записи додаються до CRM лише в робочі години; статус PARTIAL/ERROR вказує на збій одного чи кількох джерел. Підключення cron-job.org — після успішного preview. Необхідний fine-grained PAT з Actions: write лише для цього репозиторію, без Contents: write. Нативний GitHub cron не використовується.

## v0.5: пілот, ROR, звіти та контроль черги
- `pilot` — одноразовий запис фактичних нових закупівель і записів реєстру ROR, дозволений поза графіком для інтеграційної перевірки. Дані позначені для ручної оцінки. Зовнішні листи не надсилаються. Повторний запуск не додає ті самі ідентифікатори.
- ROR: безкоштовний API v2, обмежена ротаційна вибірка українських установ за трьома напрямами EDU-01, EDU-07, NGO-12. Це лише часткове покриття 115 категорій, попередня класифікація. ROR не є підтвердженням партнерства чи згоди.
- `queue-audit` — лише перевірка вже заповненої вручну черги: відмови, недійсні адреси, попередні звернення, повтори, дата перевірки, явно зафіксована згода/запит. Перевірка не замінює ручне підтвердження доказів і не надсилає пошту.
- `report-preview` — агрегована статистика без надсилання; `report` — один звіт на власну перевірену пошту у Пн–Пт о 17:30–17:59. Повторні спроби після невизначеного результату не надсилаються автоматично.

## Підключення cron-job.org
Створити fine-grained personal access token у GitHub: тільки репозиторій Prool-bot/ngo-grants-outreach, repository permission Actions: Read and write; решта без доступу, крім обов'язкового Metadata: Read. Не публікувати токен. У cron-job.org створити два завдання, timezone Europe/Istanbul. Для обох HTTP POST на https://api.github.com/repos/Prool-bot/ngo-grants-outreach/actions/workflows/outreach.yml/dispatches, заголовки Authorization: Bearer <PAT>, Accept: application/vnd.github+json, Content-Type: application/json. Завдання 1: cron `0 9-17 * * 1-5`, body `{"ref":"main","inputs":{"mode":"monitor"}}`. Завдання 2: cron `30 17 * * 1-5`, body `{"ref":"main","inputs":{"mode":"report"}}`. HTTP 204 або інша успішна відповідь означає лише прийняття запиту, перевірити Actions і журнал. Якщо токен закінчився, замінити в налаштуваннях обох завдань. Нативного GitHub schedule немає. IMAP раніше завершився таймаутом; автоматичне опрацювання поштових відповідей і повернень ще не реалізоване.

## v0.6 — контроль якості діючого реєстру
Режим registry-audit переоцінює закупівлі за поточним днем і профілем послуг; змінює лише автоматичні статуси, зберігаючи ідентифікатори, назви, джерела й усі ручні рішення. Під час monitor виконується після успішного пошуку. Перед змінами перевіряє, чи реєстр не змінився, після змін перевіряє результат. Статуси LOW_RELEVANCE, EXPIRED, EXCLUDED_SECTOR, EXCLUDED_NAVIGATION не є актуальними можливостями; VERIFY_ELIGIBILITY також не означає підтвердженого права подання.

## Партнерська комунікація
Порядок добровільної реєстрації, текст форми та публічного запрошення: [docs/partner_intake.md](docs/partner_intake.md). Це документація, не розгорнута форма. Черга звернень не поповнюється автоматично з реєстрів організацій або закупівель. Зовнішнє масове надсилання відсутнє; для підтвердженої підписки потрібна відповідна поштова платформа та окреме налаштування. Наявний SMTP використовується для звіту власнику та технічного самотестування.

## v0.7.1 — контроль звітності
Перший плановий день моніторингу — 30.11.2026. Попередні дні не зараховуються як пропуски. Режим report-self-test надсилає один тестовий звіт лише на перевірену власну пошту, має окремий ключ дедуплікації й не позначає плановий звіт виконаним. Для фактичного надсилання планового звіту використовується режим report; report-preview лише перевіряє обчислення. Аналітика CRM відокремлює архів, непідтверджені дедлайни й закупівлі для оцінки права подання.
